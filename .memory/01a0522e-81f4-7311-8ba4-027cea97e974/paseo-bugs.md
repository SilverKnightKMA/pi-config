## Bugs documented in `HANDOFF-observational-memory.md`

- **`notify()` dropped mid-turn** — use `pi.sendMessage` for any feedback that must reach the agent during a turn.
- **`getInputQuestionTitle` placeholder** — when `optional`/`skip` overrides the title, the shown title becomes `'Optional response'` instead of the configured override.

## New findings this session (2026-08-30)

- **`message_main` queue-flush self-deadlock** (CONFIRMED real, not as-designed; FIXED and E2E-verified). Root cause: a `flushWhenIdle` `setTimeout` polling `get_agent_status` every 5s keeps the parent's daemon activity window alive via its own authenticated POST traffic, so the daemon never reports idle. Three reinforcing bugs: stale `running` status, single-shot `pendingToMain[0].agentId` capture, single-slot `flushTimer` scheduler, no `session_switch`/`shutdown` cleanup. Doc comment at `paseo-channel.ts:13-15` claimed `agent_end` is observed via polling — implementation had zero `agent_end`/`agent_settled`/`turn_end` listeners. Ledger timeline confirmed 33-minute delay between queue and delivery; manual STOP + new user message was the only workaround. User's original symptom in Vietnamese: "session chạy mãi không ngừng" (session runs indefinitely). Secondary theory: OM observer subprocess POSTs may also contribute to parent appearing busy. Original child-side scout call ID: `CHANNEL_OK be46a8af`, queued call `f0ac56fb...`. **Fix**: file-queue both directions + 3-event drain (`turn_end`/`before_agent_start`/`agent_settled`) + atomic rename-based splice + `inFlight` guard. **Phase 1 + Phase 2 implemented**, **52/52 unit tests pass**, **TSC CLEAN**, **dev==live synced**, **E2E verified** with `PINEAPPLE-42` round-trip via `ask_question` absorb path. After Paseo restart at 12:34, queue drained in ~5 s via `before_agent_start`. Full diagnosis and implementation timeline in `message-main-bug.md`.

- **Self-introduced JSON-RPC `id` drop bug** (FOUND + FIXED 12:45). After the assistant's Phase 1 rewrite of `paseo-channel.ts`, every `spawn_subagent` via extension's `mcpCall` returned `Spawn failed: no MCP response (http 202)` with empty body and no agent created. Per JSON-RPC 2.0, an id-less request is a notification — the daemon processes it but never replies, and Express returns 202. Both dev and live copies were missing the `id` field; old code had `id:1` and worked that morning. The Paseo daemon restart at 12:34 was a red herring. Diagnostic arc: loopback URL+token identical between `mcpCall` and raw `Bun.fetch`; raw probes with same payload returned HTTP 200; same-process pair tests showed raw always 200 and `mcpCall` always 202; verbatim copy of `mcpCall` in standalone script returned 200 (proving the live module differed from the dev copy that was being read); debug-log patch confirmed `[mcpCall] create_agent -> 202` empty body. Fix: `let callSeq = 0; body.id = ++callSeq` per call, with a code comment warning the `id` field is mandatory. Side note: the assistant's own pi process loaded extensions at 12:35 BEFORE the fix, so its in-memory `mcpCall` still had the id-less bug at the moment of the fix — fresh children load the fixed disk code. After the fix, `paseo_create_agent` (the 39+ `paseo_` prefixed MCP tool) confirmed spawn working again.

- **Paseo "finish notification drop" stop-bug** (CONFIRMED real; daemon-side; not fixable from extensions). Symptom: working icon keeps spinning and timer keeps running with NO streaming, thinking, subagent waiting, or tool call visible — yet the user's last question already received a complete answer. Cause: daemon records `attentionReason: finished` while status stays `running`, and the finish signal never reaches the UI, leaving the spinner and timer running. Reproduced at 14:05-14:07 (daemon marked finished at 14:05:54.233 while status stayed `running`; user's "Tại sao còn pause?" arrived at 14:05:54.670 — only 0.4s after daemon-side finish); reproduced again at 21:18 (recurrence). Three symptoms from one root cause: spinner keeps spinning, timer keeps running, new user messages get swallowed/queued as `followUp` until STOP forces an abort and releases the queue. Workaround: if the answer looks complete, press STOP — safe (nothing lost, the turn already finished) and it frees stuck messages; or send a new message. The earlier 13:44 user stop was a case-A stop (silent long tool execution, `sleep 50`) — incorrect because the agent was only in the sleep, causing a System Error abort and lost turn progress. Three reproductions available; upstream bug report candidate.
  - Secondary hypothesis: OM fires an `'om: observer started'` notification after each turn's final line, which the UI might interpret as ongoing activity and keep the spinner running; proposed a cheap experiment of watching whether the spinner sticks exactly when that notification appears, and if so making OM suppress that notification.

## Environmental findings (yt-dlp + ffmpeg + pi-web-access)

- **yt-dlp JS runtime requirement (REAL, FIXED)**: youtube URL extraction in `pi-web-access` requires a JS runtime; without one, `yt-dlp` warns `No supported JavaScript runtime could be found` (exit code 2) and YouTube signatures are unsolvable. Symptom: `fetch_content` mode=answer on a YouTube URL produced a misleading `ffmpeg failed: ...` banner instead of the real yt-dlp error, because the empty format list causes `yt-dlp -g URL` to return no video stream URL and ffmpeg opens a nonexistent input.
- **Fix**: create `/home/coder/.config/yt-dlp/config` containing `--js-runtimes node` (node lives at `/usr/local/bin/node`). `yt-dlp -v` then logs `User config /home/coder/.config/yt-dlp/config: [--js-runtimes node]` and `JS runtimes: node-24.16.0`. With runtime, the tool's exact call `yt-dlp --print duration -g URL` (no `-f`, default `bv*+ba/b` format) is stable 3/3 — prints duration plus two DASH stream URLs. Fix is global; no edit to the npm package.
- **ffmpeg DASH-stream SIGSEGV (REAL, FIXED)**: johnvansickle.com static `ffmpeg 7.0.2` segfaulted (exit 139, SIGSEGV) when reading the DASH stream URL directly with the tool's command (`ffmpeg -ss <seconds> -i <streamUrl> -frames:v 1 -f image2pipe -vcodec mjpeg pipe:1`), producing an empty output file. Verified on the downloaded `me.mp4.webm` (320x240): `ffmpeg -ss 8 -i me.mp4.webm -frames:v 1 -f image2pipe -vcodec mjpeg pipe:1` exits 0 with valid 13786-byte JPEG at `/tmp/pipeout.jpg`.

## Subagent spawn model-override semantics (verified by code read at 14:03)

- `resolveModel(model, available)` strictly maps a `.md` model pin onto a model the machine has (returns `undefined` if none matches, with `MODEL_FALLBACK` patterns).
- Model resolution precedence in `index.ts`: role `.md` pin (strict, wins over everything, override param ignored; unpinned-model unavailable triggers `MODEL_FALLBACK` then refuses spawn) → caller params.model override (must be in scoped models list) → guided-choice text instructing caller to re-call.
- Thinking resolution: pin makes it fixed; non-reasoning model (lacking `[T]` tag) forced to `off`; thinking levels enum `off|minimal|low|medium|high|xhigh|max`; provider family `'pi'`.
- Tool description says spawn `model` param is `'Ignored when the role pins a model in its .md'`, which contradicts the override behavior — the description is misleading; the actual contract is that role-pin strictly wins.
- `providerStringFor(model, providerFamily='pi')` returns `'pi/<provider>/<model>'` (e.g. `'cli-openai/zaicp/glm-5.3'`).
- Spawn guidance tells the agent to pick a `[V]` vision-tagged model for image tasks since text-only models cannot see images at all, and `[XL]`/`[L]` models for longer outputs.
- Spawn model param is NOT a security boundary (only quality/cost); real boundaries are role-declared tool allowlist and extension-stamped labels `subagent.role`/`subagent.parent`. `create_agent` payload is built by extension, not the model.
- `scan-vision` scout `fa19ce57` actually ran `MiniMax-M3` (scout.md pins it), not `glm-5.3-flash` as attempted, because the override was ignored — confirmed via `paseo_get_agent_activity` on archived id.
